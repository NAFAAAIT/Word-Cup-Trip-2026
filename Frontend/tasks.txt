# خطة المهام التفصيلية

## 3) تجربة المستخدم الأساسية: اختيار مباراة -> عرض الملعب / الفنادق / المطاعم / طرق الوصول + مشاركة الموقع

**التقدير الزمني:** 10 - 14 ساعة

### الهدف
- المستخدم يختار مباراة من الصفحة الرئيسية أو صفحة المباريات.
- تظهر له صفحة تفاصيل موحدة فيها الملعب المرتبط بالمباراة.
- تعرض الصفحة الفنادق القريبة، المطاعم القريبة، وطرق الوصول للموقع.
- يستطيع مشاركة موقعه الحالي أو فتح الاتجاهات للوصول للملعب.

### المهام الفرعية
- [ ] تثبيت مصدر بيانات المباراة والملعب بحيث تكون المباراة مرتبطة بـ `stadiumId` و `cityId` بدل النصوص فقط.
- [ ] بناء صفحة تفاصيل المباراة لتعرض:
	- اسم الفريقين.
	- التاريخ والوقت.
	- اسم الملعب.
	- المدينة والدولة.
	- نوع المباراة أو المجموعة.
- [ ] ربط صفحة المباراة ببيانات الملعب الحقيقية من MongoDB.
- [ ] عرض بطاقة الملعب داخل صفحة التفاصيل مع:
	- صورة الملعب.
	- السعة.
	- المدينة والدولة.
	- وصف مختصر.
- [ ] جلب وعرض الفنادق القريبة من الملعب.
	- ترتيب الفنادق حسب القرب أو التقييم.
	- إظهار الاسم، المسافة، السعر، التقييم، والصورة.
- [ ] جلب وعرض المطاعم القريبة من الملعب.
	- ترتيب المطاعم حسب القرب أو التقييم.
	- إظهار الاسم، نوع المطبخ، المسافة، التقييم، والصورة.
- [ ] إضافة قسم "طرق الوصول" للملعب.
	- سيارة.
	- النقل العمومي.
	- المشي إذا كان قريب.
	- روابط أو أزرار لفتح الخرائط الخارجية.
- [ ] إضافة ميزة مشاركة الموقع الحالي.
	- طلب إذن الموقع من المتصفح.
	- التقاط `latitude` و `longitude`.
	- إنشاء رابط مشاركة أو فتح الخريطة على موقع المستخدم.
- [ ] إضافة زر "احصل على الاتجاهات" لفتح Google Maps أو الخريطة الداخلية.
- [ ] إضافة حالات تحميل واضحة أثناء جلب البيانات.
- [ ] إضافة رسالة خطأ إذا لم يتم العثور على مباراة أو ملعب أو بيانات قريبة.
- [ ] إضافة fallback إذا فشل API: استخدام mock data أو رسالة بديلة واضحة.
- [ ] اختبار التجربة على الهاتف والسطح المكتب.
- [ ] اختبار التدفق الكامل:
	- اختيار مباراة.
	- مشاهدة الملعب.
	- مشاهدة الفنادق.
	- مشاهدة المطاعم.
	- استخدام المشاركة أو الاتجاهات.

### ملاحظات تنفيذية
- الأفضل أن تكون صفحة المباراة هي نقطة الدخول الأساسية لهذه التجربة.
- الأفضل إعادة استعمال بيانات `stadiums`, `hotels`, `restaurants`, `matches` من API واحدة بدل fetch منفصل غير منظم.
- يجب أن تبقى التجربة سريعة وواضحة لأن هذا هو المسار الأهم للمستخدم.

## 5) تسجيل الدخول / الصلاحيات في الواجهة الأمامية

### الهدف
- المستخدم لا يستطيع الدخول لصفحات الإدارة أو تعديل البيانات بدون حساب.
- بعد تسجيل الدخول يتم تحديد الدور `admin` أو `user`.
- فقط `admin` يشوف ويدخل للداشبورد والإجراءات الحساسة.
- باقي الصفحات تبقى مفتوحة للمستخدم العادي حسب الحاجة.

### المهام الفرعية
- [ ] ربط صفحة تسجيل الدخول مع API الحقيقية.
	- إرسال البريد وكلمة المرور.
	- استقبال التوكن وبيانات المستخدم.
	- حفظ التوكن في `localStorage`.
- [ ] إنشاء أو تحسين حماية المسارات في الواجهة الأمامية.
	- منع الدخول إلى `/admin` إذا ما كانش المستخدم مسجل.
	- منع الدخول إذا كان مسجل لكن ليس `admin`.
- [ ] التحقق من صلاحية الجلسة عند تحميل الصفحة.
	- استدعاء `/auth/me` أو ما يعادله.
	- إعادة التوجيه إلى `/login` عند انتهاء الجلسة.
- [ ] تحديث الـ Navbar حسب حالة الدخول.
	- إظهار Login / Sign Up إذا المستخدم غير مسجل.
	- إظهار Logout أو الوصول للإدارة إذا المستخدم Admin.
- [ ] منع أزرار التعديل والحذف في الواجهة العامة.
	- الأزرار الإدارية تظهر فقط داخل الداشبورد.
	- الصفحات العامة تبقى للقراءة فقط.
- [ ] إضافة Logout واضح.
	- حذف التوكن.
	- حذف بيانات المستخدم من التخزين المحلي.
	- الرجوع للصفحة الرئيسية أو صفحة الدخول.
- [ ] تحسين رسائل الخطأ في login.
	- كلمة مرور خاطئة.
	- مستخدم غير موجود.
	- مشكلة شبكة.
- [ ] إضافة loading state أثناء التحقق من الصلاحيات.
- [ ] التأكد أن تحديث الصفحة لا يكسر session.
- [ ] اختبار حالات:
	- مستخدم غير مسجل.
	- مستخدم عادي.
	- Admin.
	- تسجيل خروج ثم محاولة الوصول للداشبورد.

### ملاحظات تنفيذية
- الأفضل الاعتماد على `ProtectedRoute` واحد وواضح بدل تكرار نفس المنطق في كل صفحة.
- يجب أن تكون الصلاحيات مفروضة في الواجهة الأمامية وفي الخلفية أيضًا.
- يجب التعامل مع `401` و `403` بطريقة نظيفة وتلقائية.
